# Bot Mode compatibility

Hermetic integrates the Hermes version pinned by its release. This contract note records the source-qualified behavior used by the Bot Mode implementation; it is not a report of live fleet validation or a claim of complete Desktop parity.

The implementation baseline was Hermes `v2026.9.14`, commit `345cd2b057a452236de401d3534b8502a7465e8d`; the pin is now `v2026.9.24` (0.21.5, commit `f97608f178d1ffeca59860195ab7da295f7c8e5f`), audited against every contract below. Source line references that predate the bump cite `v2026.9.14` unless they say otherwise — at `v2026.9.24` the `hosted_rooms.py` conflict check is at 964 (was 946), the event-log function at 1140 (was 1123), its `ORDER BY`/`latest_seq` read at 1163-1175 (was 1145-1157), and the cron `GET` route at `cron.py:233` (was 211).

One contract is new at the bump. From `v2026.9.21` the gateway delivers server→client requests — approvals, clarifications, sudo and secret prompts — only to a client on the session that has sent `client.capabilities {server_requests: true}`; with none attached it withdraws an approval at once and resolves a clarify to nothing (`tui_gateway/server_requests.py:117-122`). Hermetic sends it first on every socket a turn is read from — the one that submits the prompt and the one a dropped turn reconnects on (`advertiseServerRequests`) — and on no other, since a socket that claims the capability without surfacing prompts would make a prompt sent to it alone wait out its deadline. An older gateway answers `-32601` and behaves as before.

## Conversations and scope

A canonical conversation is the exact `Bot Chat` title in one Hermes profile. It is not the newest session. Registry identity and the current compression successor may differ. Creating a canonical session must persist its title before submitting a prompt and adopt the winning session if another client creates it concurrently. Passive roster and transcript reads must not create sessions or run models.

Every operation carries its instance and profile. A rejected scoped request must never be retried as an unscoped request. Provider credential profiles in Hermetic remain distinct from Hermes bot profiles.

`bots.capabilities` is a live probe, not an inference from the adapter's own shape: it reads the profile roster (`profiles.list`), the routine registry (`GET /api/cron/jobs?profile=<profile>`, scoped to a profile the roster just named) and the hosted-room protocol (`groups.capabilities`), in that order, because the routine probe needs a profile from the roster. Two outcomes are not the same thing. A **refused** capability is the gateway's own settled answer — the endpoint 404s, 403s or 409s — and is worth remembering: it is cached for five seconds, keyed per fleet and instance. An **unknown** capability is a probe that never landed at all — a transport fault, a malformed body, the caller's own abort — and caching it would turn one hiccup into five seconds of a feature the gateway has being reported as a feature it does not; it is never memoized, and the caller must re-probe to learn anything. Heads must render this distinction rather than collapsing both onto one boolean: `refused` says why and offers no retry, `unknown` says the app does not know and offers one that genuinely re-asks the gateway.

## Dashboard transport

The gateway uses authenticated JSON-RPC over `/api/ws` for session, profile and hosted-room operations. Some complete dashboard workflows also require authenticated REST. Hermetic keeps those wire details in private adapters rather than exposing an arbitrary gateway proxy to the page.

The pinned source provides these additional REST contracts:

| Operation | Dashboard contract |
|---|---|
| List profile jobs | `GET /api/cron/jobs?profile=<profile>` |
| Create profile job | `POST /api/cron/jobs?profile=<profile>` |
| Edit job | `PUT /api/cron/jobs/<id>?profile=<profile>` with `{updates: ...}` |
| Pause or resume job | `POST /api/cron/jobs/<id>/pause` or `/resume`, with explicit `profile` |
| Run job now | `POST /api/cron/jobs/<id>/trigger?profile=<profile>` |
| Read job runs | `GET /api/cron/jobs/<id>/runs?profile=<profile>&limit=<n>` |
| Remove job | `DELETE /api/cron/jobs/<id>?profile=<profile>` |
| Remove bot profile | `DELETE /api/profiles/<name>` |

The routine probe `bots.capabilities` performs is this same read (`GET /api/cron/jobs?profile=<profile>`, `hermes_cli/web_routers/cron.py:211`), scoped to a profile the roster named rather than left to the route's own `profile="all"` default, and never retried unscoped on a refusal.

`cron.manage` alone only exposes list, add, remove, pause and resume at this pin. It does not provide edit, run-now or run-history actions. The REST create model and RPC add model also differ; callers must not assume that fields accepted by one are accepted by the other.

Manual job execution shares the scheduler's durable claim. A conflict can mean that another scheduler already claimed the job, and must not trigger an automatic retry. Running a paused job can resume it. A completed one-shot job may disappear from the refreshed list. Job results and history must reflect the returned upstream state.

Source: [cron routes](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/hermes_cli/web_routers/cron.py), [dashboard request models](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/hermes_cli/web_models.py), [profile routes](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/hermes_cli/web_routers/profiles.py).

Hermetic's own dashboard, downstream of all of that, does not open one subscription per conversation. `chat.subscribe` multiplexes every conversation the app's main process currently owns onto one stream (`packages/app/src/chat-owner.ts`, `chat-stream.ts`) — a fleet view watching a dozen bots would otherwise pay a subscription, a gateway socket and a reader for each. The subscriptions it carries belong to the main process rather than to a request: they are started at launch and resynced on a listen-preference change or a fleet switch, and a reader closing its stream id detaches only that reader, never the underlying observation. The stream carries only *owned* conversations — the canonical conversation of every bot on an instance the operator listens to, named on each frame as `{instance, bot, session}` with `session: null` for the canonical case — plus `dropped`/keepalive frames the transport itself emits. A conversation opened by explicit session id is not on it: `BotWorkspace.tsx` polls that transcript on a five-second timer instead, independent of any main-process observation, for as long as it is the thread on screen. This is fixture-validated behavior (`packages/app/test/chat-owner.test.ts`, `packages/ui/test/chat-observe.dom.test.tsx`, `packages/ui/test/chat-conversations.dom.test.tsx`), not validated against a live gateway.

`chat.observe`'s reconnect budget is two counters, not one, because a read failure and a hint-stream failure are unlike things (`packages/core/src/chat/chat-observe.ts`). A retryable failure of the authoritative `chat.history` read spends `readAttempt`; exhausting it is the only thing that ends the watch, with a terminal `error`. A failing live hint stream spends a separate `hintAttempt`; exhausting that instead sets the subscription to poll-only and keeps it reading on `OBSERVE_POLL_MS` forever, emitting nothing at the moment it degrades — `error` is terminal by contract and a further `reconnect` would carry an `attempt` past its own schema bound, so a head is expected to decay its own health band on inactivity rather than wait for an event that will not come. Whether a hint channel is attempted at all is gated on more than the adapter defining `observe`: that method still has to exist for a hint channel to be built at all, but on top of it a runtime "strike" memo (`hintsUsable` in `packages/core/src/chat/chat.ts`) that expires after five minutes decides whether one is attempted. Every real adapter defines `observe`, so answering only that question is what made a gateway whose hint socket closes on open look supported while delivering nothing. Source: `packages/core/test/chat-observe.test.ts` ("a hint stream that ends at once degrades to polling and keeps delivering").

The dedicated chat sockets — one per turn, one per observed conversation's hint stream, and the pooled request socket — keep themselves alive the way the Desktop client does. When `gateway.ready` advertises `heartbeat: true` (`tui_gateway/contracts/events.py`, sent by `tui_gateway/ws.py`), hermetic sends a JSON-RPC `ping` every `CHAT_HEARTBEAT_MS` (15 s) and closes the socket after `CHAT_HEARTBEAT_DEADLINE_MS` (45 s) with no inbound frame of any kind, so a tailnet drop after the first content frame closes the socket, which the turn's pump treats as a drop and reconnects from its cursor, instead of stalling forever; a gateway that does not advertise the flag is neither pinged nor timed out, because a watch socket on such a gateway is legitimately silent (`packages/core/src/chat/hermes/hermes-chat-rpc.ts`, `packages/core/test/hermes-chat-heartbeat.test.ts`). A `prompt.submit` reply is read rather than assumed: the gateway answers `streaming` for a turn it started, and `queued`, `redirected` or `steered` when `display.busy_input_mode` absorbed the prompt into a running turn (`tui_gateway/session_auto_continue.py`); the status frame carries those three literally and reports `submitted` for `streaming` or an unknown reply (`ChatStatusState`, `packages/core/src/schema/chat.ts`). The app itself never submits into a running turn: a message typed while one runs is queued in the page, FIFO per conversation, drained one at a time when the turn ends, and parked rather than dropped by Stop or by a failed turn (`packages/ui/src/chat/chat-state.tsx`, `packages/ui/test/chat-queue.dom.test.tsx`), which is the Desktop composer's queue without its `session.steer` and `session.redirect` corrections — those would be new parity surface, not something smuggled through `chat.send`. In the transcript, one assistant turn is drawn once however many durable rows Hermes stored for it: consecutive bot and tool-result rows merge in the presentation layer (`packages/ui/src/chat/chat-turns.ts`), a consecutive run of tool calls is one persistent, open-by-default group whose rows show name, target, status and duration and expand to arguments and result, and only a question, an approval, interim prose or a failure breaks the run. Continuing a dropped turn through `session.events.since` **is** mirrored. The rule is design.md §9.2, "Reconnecting continues the turn from its cursor". The pinned contract is `session.events.since { session_id, last_seen }` → `{events, latest_seq, truncated, count, epoch, open_requests}` (`tui_gateway/methods_session.py`); a fresh socket attaches with `session.resume` first, because `events.since` does not attach and the gateway fans out only to attached sockets. The cursor is the `seq` of the last event the turn applied, and a baseline probe before `prompt.submit` — `events.since` with `last_seen` at the maximum — records the session's `epoch` and starting `latest_seq` so a drop before the first new event cannot replay the previous turn as this one. Replayed events go through the same mapper as live ones and are deduped by `seq`, and `open_requests` is re-emitted so an approval raised while the socket was down still reaches the operator. Re-reading the transcript is the fallback, on conditions the log cannot serve: `truncated` (the log no longer reaches the cursor), an `epoch` that differs from the baseline, `-32601` at this pin (memoized five minutes per box, so the second turn does not ask again), a `session.resume` answering `running: false` or a different runtime id, or a spent reconnect budget (five attempts, 1 s doubling to a 16 s step, 30 s cap). Any of those ends the turn as `done incomplete`, which is what already sends the app back to the box's own copy. What is still not mirrored from Desktop: a single multiplexed socket per box, and replaying a session's `open_requests` into a thread opened while **another** client's turn is waiting on an approval — v2026.9.14 offers no read-only lookup for that, `session.resume` is not passive, and hermetic replays `open_requests` only into its own reconnecting turn.

A message body is drawn the way Desktop draws it. Upstream renders markdown with streamdown, `@streamdown/math` and katex 0.16.x; hermetic parses the markdown itself into nodes (`packages/ui/src/chat/chat-logic.ts`) and draws them as elements rather than as HTML, and hands only the TeX to KaTeX (`packages/ui/src/chat/chat-math.ts`, katex 0.16.x). So an expression a bot writes is typeset rather than shown as its source, inline and as a display block. Two things differ from the upstream renderer on purpose: KaTeX runs with `trust: false`, so the commands that can emit a URL or raw markup are inert, and an expression carrying a redaction marker is never typeset at all — core masks before the wire and the marker belongs to `RedactedText`, so the source is drawn instead. The stylesheet and its font faces ship inside the app's page, beside the vendored `Archivo` and `JetBrains Mono` faces in `packages/ui/fonts/`; nothing is fetched at render time (`packages/ui/test/chat-katex.dom.test.tsx`).

Recovering a failed conversation is targeted. `chat.observe.resume` (`ChatOwner.resume`) re-observes exactly the one conversation it names; it is not a `chat.listen` resync and does not touch any other bot's subscription, owned or guest. A reader that attaches after a conversation's watch has already failed does not see a healthy-looking thread with no explanation: the owner replays that conversation's last health event — `reconnect` mid-backoff, terminal `error` once it ended — under its own event name, after the cached snapshot, on both the single-conversation subscription and the `chat.subscribe` fan-in, so a late joiner lands in the same state a reader who watched the failure happen is in. Joining a conversation whose subscription already ended for a remembered reason replays that `error` and ends the stream rather than opening a fresh read; only `resume` restarts one. The owner pins its own (listened) subscriptions and refcounts only guest ones, so a reader going away can end a guest watch but never a main-process-owned one. Source: `packages/app/test/chat-owner.test.ts`.

Fixture mode has a staging surface for demonstrating an external arrival, since `bun run dev:fixture` has no gateway to produce one: `hermetic.fixture.chat.inject`/`.hint`, reachable as the `fixture.chat.inject` and `fixture.chat.hint` requests (`packages/app/src/handlers/fixture.ts`). `inject` appends a `user` row to the fixture box's transcript and announces it on open hint streams; `hint` announces without appending, for a row already there. Both are fixture-only by two guards, with a third layer bounding the blast radius: construction builds no `fixture` namespace outside fixture mode, and an explicitly-constructed control surface with `fixture: false` throws `UNSUPPORTED` before the input is read, while the methods themselves can reach only an in-memory activity table with no AWS client or config behind it. Neither is a `PUBLIC_METHOD` or a CLI verb; both are `MACHINERY_RPC` entries, which is how the parity test knows they exist without expecting a core method behind them. Source: `packages/app/test/handlers/dispatch.test.ts`.

## Hosted-room boundaries

`groups.capabilities` establishes whether a persistent hosted driver is available. Hosted rooms have durable ordered logs, fixed membership, user-message submission, stop, rename, approvals and disbanding. A deliberate new message resumes discussion after a stop; there is no `groups.resume` RPC and canceled work must not be replayed.

Every `RoomEvent` carries a server-owned `event_id` (`tui_gateway/contracts/groups_bot_relay.py:41`); the caller's own retry key is folded into it through `user_event_id`, which hashes the client key into the server's own namespace (`gateway/hosted_rooms.py:244`) rather than storing it verbatim. `groups.send` answers a repeated `event_id` carrying the same content with the row it already holds, flagged `idempotent`; a repeated id carrying *different* content raises `EventConflictError("event_id already exists with different content")` (`gateway/hosted_rooms.py:946`). Every `HostedRoomError` a send can raise collapses onto one numeric RPC code before it reaches Hermetic, so the adapter identifies a conflict by matching that exact message text — a wording change upstream would degrade this to an ordinary protocol error rather than a false positive, never the reverse.

`groups.log` is monotonic and gap-free under a fenced update and returns `ORDER BY seq ASC` (`gateway/hosted_rooms.py:1145-1153`); `cursor` is the highest `seq` a page answered to, or `since_seq` again for an empty page, and `latest_seq` — the room's own high-water mark — is on every response including that empty one (`gateway/hosted_rooms.py:1156-1157`). There is no tail read at this pin: no reverse flag, no `before_seq` parameter, no negative offset, on the `log` function's own signature (`gateway/hosted_rooms.py:1123`). A client that wants to open near the end of a long room has to compute its own `since_seq` from `latest_seq` instead; Hermetic does this in the room view, reading a fixed window back from the mark on first open and stating how many earlier events it chose not to read.

The inspected pin has no hosted membership-update RPC. Direct RoomLink supports text and requires a separately configured `api_server`, reachability and scoped grants. Access to the dashboard does not establish that configuration. Cross-instance rooms, membership editing and room attachments must remain unavailable until the corresponding runtime contracts are qualified. A room is not implemented by sending independent prompts to each member.

Native same-instance teammate messaging requires canonical Bot Chat sessions and the Bot Mode protocol/managed profile metadata. Inserting an `@mention` into a prompt is not proof of delivery. Sender attribution, execution and replies remain upstream responsibilities.

Source: [room and relay contracts](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/tui_gateway/contracts/groups_bot_relay.py), [hosted rooms](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/gateway/hosted_rooms.py), [canonical chat](https://github.com/NousResearch/hermes-agent/blob/345cd2b057a452236de401d3534b8502a7465e8d/apps/desktop/src/plugins/hermes-bots/canonical-chat.ts).

## Teammate messaging, mentions and silence

This section records the contracts behind these Bot Mode behaviors: intentional silence, `message_agent` deliveries and their failures, `@mention` completion, bot rename and create, compact notices, and two lifecycle corrections. Line references are at `v2026.9.24` (commit `f97608f178d1ffeca59860195ab7da295f7c8e5f`). Each contract is qualified against that source and exercised against Hermetic's fixture only; none was observed on a live gateway (see Validation boundary).

### Intentional silence

A Hermes bot can answer with a bare marker instead of prose, which means "I have nothing to say". The marker set is `[SILENT]`, `SILENT`, `NO_REPLY`, `NO REPLY`, `[静默]`, `静默`, `[沉默]` and `沉默` (`gateway/response_filters.py:19-22`). A response is silence only when the whole message matches: it is trimmed, uppercased and its whitespace collapsed, and both the raw form and the form with edge punctuation stripped are tried. Edge punctuation is any Unicode `P*` character except `[` and `]`, so `*NO_REPLY*` and `.NO_REPLY` match while a malformed `[SILENT` cannot become `SILENT`. A message longer than 64 code points is never a candidate, and a blank message is not silence (`response_filters.py:37-75`). Prose that merely mentions `NO_REPLY` is delivered normally.

While a reply streams, upstream holds back any buffer that could still resolve to a marker (`NO` on the way to `NO_REPLY`, or an exact marker not yet terminated by the end of the stream), so a raw marker is never shown and then retracted (`response_filters.py:126-137`, applied to Bot Chat sessions at `tui_gateway/prompt_turn.py:628-642`). When the turn ends, the Bot Chat completion text is blanked only for a successful turn; a failed turn deliberately fails open so its diagnostic is not swallowed (`prompt_turn.py:19-28,822-823`). The stored transcript row is untouched: the token remains an ordinary assistant row.

Upstream Desktop therefore never draws a silent turn live, because the completion arrives empty, and it has no silence rendering of its own. Reloading a transcript is the only place the token becomes visible, which is why Hermetic adds a marker. This is an addition, not parity.

In Hermetic:

- The matcher is ported verbatim into `packages/core/src/shared/silence.ts`, so the UI and core share one rule, and upstream's own test cases are replayed in `packages/core/test/silence.test.ts`.
- A settled turn whose closing text block is only a marker is drawn as a muted "stayed silent" line, not a bubble (`packages/ui/src/chat/chat-silence.ts`, `packages/ui/src/chat/components/Message.tsx`). A streamed prefix that could still become a marker is held back behind the caret until it diverges into an answer. A failed or cut-off turn is never drawn as silence, whatever its text says. Hosted-room member posts that are only a marker get the same line (`packages/ui/src/chat/components/RoomConversation.tsx`). Tests: `packages/ui/test/chat-silence.dom.test.tsx`, `packages/ui/test/room-conversation.dom.test.tsx`.
- A silent reply produces no inbox row, and the rail previews it as silence rather than as the token (`packages/core/src/chat/chat-activity.ts`, `packages/core/src/chat/notifications.ts`; `packages/core/test/notifications-chat.test.ts`).

Known gap: a reloaded transcript cannot always tell a failed `NO_REPLY` turn from a silent one. Upstream fails open on a failed turn, but the stored row carries the same text either way, so Hermetic can distinguish them only when the box stamps an error on the row.

### Teammate messages (`message_agent`)

A bot messages a teammate with the injected `message_agent` tool, whose arguments are `{target, message}` (`tools/bot_mode_dm.py:64-117`). The call is fire-and-forget: it validates the target against the live roster, queues a background delivery into the target's own Bot Chat, and returns at once with `{status: "queued", delivery_id, to, reply_delivery, detail, process_id, queued_at}` (`bot_mode_dm.py:680-688`). An error returns `{error, reason}` and, for an unknown target, the `teammates` and `peers` lists (`bot_mode_dm.py:187-195`). The recipient's reply does not come back as a tool result. It returns to the sender as the completion of the background process, which wakes the sender's next turn. The `reason` codes are upstream's (`tools/bot_failure_reasons.py:17-37`, plus `target_busy`, `bot_mode_dm.py:446`). Upstream has no human-facing label for any of them, so the words Hermetic shows are its own (see "Failed deliveries and Retry" below). The tool never retries itself; upstream's delivery runner already retries a transient reason once, and Hermetic does not resend on its own.

The delivery runs a turn on the user role in the target's Bot Chat, so it is stored as an ordinary `user` row signed `Message from 🤖 <display> (@<handle>): <body>` (`bot_mode_dm.py:238`). When the relay carries a delivery from another machine, it rewrites the handle in that stamp to the form this gateway can reply to, `(@handle@connection)` (`tools/bot_relay.py:239-254`). Desktop recognizes the signature with `AGENT_MESSAGE_RE` (`apps/desktop/src/components/assistant-ui/thread/user-message.tsx:90-91`) and does not draw it as the operator.

In Hermetic, core owns the upstream-specific part. `packages/core/src/chat/hermes/bot-delivery.ts` lifts a delivery's signature into `ChatMessage.from_bot` (`{name, handle, connection?}`) and strips it from the body. It departs from Desktop's regex in two ways, on purpose:

- Tighter. Desktop makes the 🤖 glyph and the `(@handle)` optional, so an operator who types "Message from HR: the offsite moved" is drawn as a bot. Upstream builds the stamp exactly one way (`bot_mode_dm.py:238`) and the relay's rewrite regex requires both (`bot_relay.py:239`), so Hermetic reads a row as a delivery only when it carries the glyph and `(@handle)` or `(@handle@connection)`, or is the exact legacy `[Message from agent '<name>']` form. Desktop still parses that legacy form, so it is kept, though no v2026.9.24 Python emits it. Anything else, "Message from HR: …" included, stays operator text. Because the glyph and the handle are both required, the name itself can be looser than Desktop's `[^:\n(]`: a friendly name may hold `(` or `:` (`QA (nightly)`, `Ops: Night`), and Hermetic now lets you create such titles, so the name is any text on one line up to 64 characters, read lazily the way upstream's own `_SENDER_STAMP_RE` reads it (`.+?`, `bot_relay.py:239`). The lazy match ends the name at the first ` (@handle): `, so `Message from 🤖 QA (nightly) (@qa): hi` is `QA (nightly)` saying `hi`, and a body that quotes another stamp further on stays body. The rail's preview of a delivery uses the same parser (`eventPreviewOf`, `hermes-chat-sessions.ts`).
- Capturing. Desktop's connection group is non-capturing. Hermetic captures it as `from_bot.connection`, so a head knows that `(@scribe@laptop)` is the `scribe` on `laptop` and never resolves it to this box's `scribe`.

`packages/core/src/chat/hermes/hermes-chat-blocks.ts` tags the sender's tool block `render: "message_agent"`. Test: `packages/core/test/bot-delivery.test.ts`.

The UI draws each end as an event, not as a bubble and not as a tool card:

- The sender sees "Messaging <bot>…" while the call runs, "Messaged <bot>" once it is queued, and "Couldn't message <bot> · <reason>" on an error acknowledgement, where the reason is a label for upstream's code (`packages/ui/src/chat/components/BotDm.tsx`, `packages/ui/src/chat/bot-dm.ts`, `packages/ui/src/chat/bot-dm-reasons.ts`).
- The receiver sees the delivery attributed to the sending bot, with a "Message from <bot>" marker (`packages/ui/src/chat/components/Message.tsx`).
- Either marker opens an exchange panel (`packages/ui/src/chat/components/BotExchange.tsx`). It reads the target's canonical Bot Chat through `chat.history`, finds the delivery by the sender's handle and the message body, and shows the replies after it. When the box has not run the delivery yet, it says so and falls back to the reply carried by the delivery's completion notice in the sender's transcript, matched by `process_id`.

Tests: `packages/ui/test/bot-dm.dom.test.tsx` and `packages/ui/test/flows/bot-dm.flow.test.tsx`.

#### Targets on another machine

The acknowledgement's `to` names where the message went, in one of three forms: `@<handle>` for a bot on this box (`bot_mode_dm.py:282`), `@<agent> on peer '<peer>'` for a registered peer (`:262`), and `@<handle> on <connection label>` for a relayed one (`:315,:325`). A refused or still-running call has no acknowledgement, so the marker falls back to the target the model wrote, which names another machine only as `<peer>/<agent>` (`_PEER_TARGET_RE`, `:54`) or `<handle>@<connection>` (any target with an `@` goes past the local roster, `:268`). A bare target is assumed local. A destination on another machine is never resolved to a local bot, however its handle reads, because a same-named bot here is a different bot; the marker shows the name and where it lives (`dmDestination` and `dmTarget`, `packages/ui/src/chat/bot-dm.ts`). The receiving side follows the same rule through `from_bot.connection` (`dmSender`). Test: `packages/ui/test/bot-dm.dom.test.tsx`.

Sending the same body to the same bot twice makes two deliveries, so `findExchange` (`packages/ui/src/chat/bot-dm.ts`) claims deliveries newest call first. `callSends` collects the later calls in the thread that sent the same body to the same bot; working back from the newest, each takes the latest unclaimed delivery stamped no more than `DELIVERY_SKEW_MS` (1 s) before it, and the opened call claims last. The tool-call row is persisted before the tool's side effects run (`agent/turn_tool_round.py:118-121`), so a delivery cannot predate the call that made it, and the tolerance only absorbs clock skew between the two rows. A call whose delivery is missing, because it was never written or has rolled out of the transcript, therefore loses only its own: every later call's window starts after it. Two calls in one turn share a stamp and still map in order. The one case this order gets wrong is a same-turn pair whose second delivery has not been written yet: the second call shows the first's delivery until its own lands. When a call finds none, the exchange says so and shows the completion notice's reply, which is keyed by process and cannot be the wrong one.

#### Failed deliveries and Retry

`packages/ui/src/chat/bot-dm-reasons.ts` maps every code in `bot_failure_reasons.py:17-37`, plus `target_busy`, to a label, a sentence of guidance and a retry flag. The marker shows the label in its summary and, folded behind it, the guidance, upstream's own error text and the `teammates` or `peers` list when upstream sent one. Upstream has no human labels for these codes (Desktop never reads them), so the labels and guidance are Hermetic's, leaning on upstream's own sentences where it has them.

The retry flag follows upstream's policy:

- `runtime_offline`, `delivery_timeout`, `provider_rate_limit` and `provider_server_error` are upstream's `AUTO_RETRYABLE` set (`bot_failure_reasons.py:40`).
- `context_overflow` retries after compression, by `retry_action` (`:62-63`).
- `target_busy` retries because upstream's own refusal tells the sender to try again (`bot_mode_dm.py:445`, `bot_relay.py:625`).
- `queued_expired` retries as a judgement call: upstream's sentence says to resend once the Desktop reconnects (`bot_relay.py:327-328`), but the code is outside `AUTO_RETRYABLE`.
- `provider_auth_or_access`, `provider_quota_limit`, `missing_config`, `model_unavailable`, `agent_blocked`, `cancelled` and `unknown` never retry: a retry cannot fix them and only burns quota (`bot_failure_reasons.py:47-51,64`).

A code this build does not know reads as a generic failure with no Retry. A retryable code is not enough on its own (`dmRetryable`): `_err` classifies every refusal by its text (`classify_agent_error`, `bot_mode_dm.py:187-195`), so a resolution error can arrive with a retryable reason — "No teammate named 'rate-limiter'…" reads as `provider_rate_limit`. A refusal that carries `teammates` or `peers` is a resolution error, since `_err` attaches them to nothing else, and gets no Retry whatever its reason. So do the refusals that carry no roster but cannot be fixed by sending again, matched on the opening of upstream's own sentence (`bot_mode_dm.py:209-283`): the Bot Chat and Bot-Mode-managed gates, `message is required`, `message too long`, `target is required.`, `No registered peer named`, `Invalid target:`, `You can't message yourself.`, `No teammate named`, the relay's `exists on several connected machines`, and any sentence that says "do not retry". A wording change upstream falls back to the reason's own flag. Retry is also withdrawn once a later `message_agent` call in the same thread sent the same body to the same bot (`recoveredDms`): the bot already recovered, and asking again would send the message twice.

Retry does not re-run the tool. It sends an operator message to the sending bot, through the thread's normal send path, asking it to make a fresh `message_agent` call; one ask per call. The thread remembers which calls were asked for, by tool id, so a marker that remounts (a re-read history, a re-merged turn) keeps "Asked … to retry" instead of offering the button again. The tool never retries itself, and upstream's delivery runner has already retried a transient reason once.

Only the tool's own result reaches this marker. In practice that is an `unknown`-classified error or `runtime_offline`. `target_busy` and `queued_expired` reach the sender as a completion notice whose `reason` the marker does not render yet. Tests: `packages/ui/test/bot-dm-reasons.test.ts`, `packages/ui/test/bot-dm.dom.test.tsx`.

#### Rail unread and previews

A delivery rides the user role but is not the operator's. A delivery that carries a handle marks the receiving bot unread on the rail, as a reply does; the operator's own rows still do not (`packages/ui/src/chat/chat-conversations.ts`). Rail previews carry `preview_role` where Hermetic knows the row they quote: a preview rewritten from a delivery is `user`, one from a background-process notice is `system`, and one built from a transcript row has its own role (`eventPreviewOf`, `packages/core/src/chat/hermes/hermes-chat-sessions.ts`). Upstream's roster preview selects the newest `user` or `assistant` row's `content` alone and carries no role (`tui_gateway/methods_profiles.py:105-117`), so most previews are role-null. A bare silence token with no known role still reads "stayed silent", since the newest row of a Bot Chat that is only a marker is overwhelmingly the bot's; only a known `user` or `system` role shows the text literally, so the operator's own "No reply" is not drawn as the bot's silence (`isSilentPreview`, `packages/ui/src/chat/chat-silence.ts`). Tests: `packages/core/test/hermes-chat.test.ts`, `packages/ui/test/chat-observe-rail.dom.test.tsx`, `packages/ui/test/chat-silence.dom.test.tsx`.

This departs from Desktop on purpose. Desktop draws a delivery as a centred, collapsed notice (`agent-delivery.tsx`) and collapses the receiver's reply under "Replied to <sender>" (`assistant-message.tsx:106-206`, covered by `inter-agent-collapse.test.tsx`). It has no `message_agent`-specific renderer and no click-through. Hermetic does not collapse the reply, and it opens the exchange because the two halves of a message live in two transcripts, and reading one without the other is how a reply gets missed.

### Mentions

Completion follows Desktop. Typing `@` at a token boundary opens the list (`AT_TRIGGER_RE`, `apps/desktop/src/app/chat/composer/text-utils.ts:65`). The typed prefix narrows it case-insensitively against the tag, the handle and the friendly name; roster order is kept, the current bot is excluded, and at most eight rows show (`apps/desktop/src/plugins/hermes-bots/plugin.tsx:139-200`). The primary profile is offered as `@hermes`, never `@default` (`data.ts:1011-1017`, server side `tools/bot_mode_probe.py:67-69`). The tag that is inserted is the slug of the bot's friendly title when it has one, and its handle otherwise (`data.ts:1019-1075`). A slug and a collapsed form are both accepted by the resolver, and the reserved tokens `all`, `everyone`, `user`, `default` and `hermes` are dropped from them so a bot titled "Hermes" cannot take over the primary alias (`bot_mode_probe.py:178-189`).

Hermetic ports these rules in `packages/core/src/shared/bot-handles.ts` (shared with the box-side resolver) and `packages/ui/src/chat/chat-mentions.ts`. One picker, `packages/ui/src/chat/components/MentionPicker.tsx`, serves the bot composer and the hosted-room composer. A room composer inserts the member's handle rather than a friendly slug, because the gateway matches `@handle` against its frozen member roster with `_MENTION_RE` (`gateway/hosted_room_discussion.py:38,302-318`). It matches registered handles only, case-insensitively, and a mention that names no member is ignored. Hermetic therefore registers the default profile in a new room as handle `hermes`, as `message_agent` and Desktop name it (`tools/bot_mode_probe.py:67-69`), and a duplicate check counts `default` and a legacy profile directory named `hermes` as one handle. Membership is fixed at creation, so a room created earlier keeps `@default`; the room picker finds the default bot under either name and inserts the room's own handle (`packages/ui/src/chat/components/RoomConversation.tsx`, `packages/core/src/chat/bot-mode.ts`, `rooms.create`). Tests: `packages/core/test/bot-handles.test.ts`, `packages/core/test/bot-mode.test.ts`, `packages/ui/test/chat-mentions.test.ts`, `packages/ui/test/chat-mentions.dom.test.tsx`.

Mentions are same-instance only. Desktop's `@tag@connection` form for bots on other connections, and its on-submit note that resolves `@mentions` from the Bot Mode roster, are not mirrored. Hermes resolves a `message_agent` target itself, by profile name, friendly name or Desktop `@slug`, and rejects an ambiguous name rather than guess (`bot_mode_dm.py:167-184`).

### Renaming a bot

A bot's friendly title lives in the profile's `ui_meta['hermes-bots']` namespace, written through `profiles.configure {name, ui_meta, ui_meta_expected_revisions}` (`tui_gateway/methods_profiles.py:625-648`; Desktop's Edit Profile writes `title` and `custom: true`, `edit-profile-dialog.tsx:104-112`, via `saveBotMeta`, `data.ts:314-435`). Upstream replaces `ui_meta` one top-level key at a time, with a per-key revision for compare-and-swap: a mismatched revision rejects the whole write and reports `ui_meta_conflicts`, and revisions survive deletion so a stale client cannot recreate a removed key (`methods_profiles.py:487-530`). Because the namespace is replaced whole, a title sent alone would drop every other key Desktop keeps there.

`bots.update` with `title` therefore reads the namespace and its revision from `profiles.list`, merges `title` into it and leaves every other key, `custom` included, as it was (`custom` is Desktop's avatar flag, `types.ts:72`). A null or empty title writes `title: ""`, which is how Desktop's own reset reads, rather than deleting the key, since Desktop merges its cached copy under the server's and would restore a deleted title on its next save. The title goes in its own `profiles.configure` call, before any other field in the same update, because upstream applies each section independently: a refused title then writes nothing. A row with no `ui_meta_revisions` (the gateway's feature-detect for this compare-and-swap, `methods_profiles.py:242-243`) is refused rather than written blind. The write carries the revision it read, so a concurrent Desktop save is a `CONFLICT` and not a silent overwrite (`packages/core/src/chat/bot-mode.ts`, `titleMeta`). Desktop's own `saveBotMeta` sends no expected revision on this path (`data.ts:356-368`; only room saves do, `group-chat.ts:1176-1185`), so this is stricter than Desktop. The roster shows the title with Desktop's precedence: `ui_meta['hermes-bots'].title`, then the profile's `display_name`, then the profile name (`labels.ts:14-64`). The edit control is `packages/ui/src/chat/components/BotTitleEdit.tsx`, in the chat header (`packages/ui/test/bot-title-edit.dom.test.tsx`).

`bots.create` takes an optional `title` too, so a bot can be born with its friendly name. After `profiles.create`, core writes the Bot Mode namespace the way Desktop's create dialog does: `ui_meta['hermes-bots']` carries `title` and `created` (epoch milliseconds) beside the `version: 1` marker that makes the profile Bot Mode managed (`create-dialog.tsx:451-486`; `packages/core/src/chat/bot-mode.ts`, `create`; `BotCreateInput`, `packages/core/src/schema/bot-mode.ts`). Desktop's look keys (`shape`, `color`, `imageKind`) are not written. Desktop also sends `profiles.create` a description of "title — description"; Hermetic does not copy that prefix, because the teammate roster already joins the two (`_role_line`, `tools/bot_mode_probe.py:132-155`), so the title would read twice there and `bots.get` would hand the prefix back as a description the operator never typed. The create form has a "Friendly name" field. Tests: `packages/core/test/bot-mode.test.ts`, `packages/ui/test/bot-title-edit.dom.test.tsx`.

Renaming the profile directory (`PATCH /api/profiles/{name}`, `hermes_cli/web_routers/profiles.py:850-866`) is not supported. It stops a running gateway and rewrites the profile's identity, which is a different operation from a display title.

### Compact notices

`/new` and `/reset` would fork a Bot Chat, so Hermetic compacts instead, as Desktop's composer middleware does, and answers in Desktop's words: "This chat never resets. Bot chats are one continuous conversation — compacting instead." (`apps/desktop/src/plugins/hermes-bots/plugin.tsx:775-779`). Desktop's last sentence points at its Sessions mode; Hermetic's reads "For a throwaway session with this bot, start a separate session." A typed `/compact` reports the gateway's own completion status, "✓ Context compression complete" (`tui_gateway/compute_host_bridge.py:340`). A compaction the gateway did not perform reports `Compaction: <status>` either way (`compactNotice`, `packages/core/src/chat/chat-send.ts`).

### Archive, Stop and identifier bounds

Archiving a canonical Bot Chat sends no title. Upstream refuses a user title write on a hidden `Bot Chat` row, because the title is the conversation's identity (`hermes_state_titles.py:85-95`), and the session PATCH applies the title before the flags, so a title would fail the whole archive. Instead, upstream retires the name when it is next claimed: titling a new Bot Chat clears the title of an archived hidden holder in the same transaction (`hermes_state_titles.py:105-117`). The archived session keeps its history. That release is in upstream b6207cb5903, first tagged v2026.9.21. On an older gateway an archived canonical row keeps its title, so every new Bot Chat collides with it.

A title held by a session the gateway does not list (the title lookup drops archived rows, `tui_gateway/methods_session.py:461-479`) is reported as a `CONFLICT`. Upstream's refusal names the holder ("Title 'Bot Chat' is already in use by session <id>", `hermes_state_titles.py:119`), so Hermetic reads that session through `GET /api/sessions/{id}?profile=…` (`hermes_cli/web_routers/sessions.py:500-513`), which returns the full row, `archived` and `hidden` included, where no session RPC does. Upstream releases the title only when the holder is archived and hidden (`hermes_state_titles.py:108-117`), so the two flags pick the hint. Archived and hidden, which is how Hermetic archives a Bot Chat (or archived with no `hidden` in the row): this gateway is older than v2026.9.21 and has not released the title, so unarchive the session in Hermes, address it with `--session <id>`, or upgrade the gateway. Archived but not hidden, as archiving in Hermes itself leaves it: the session still holds the title on any gateway, so the error says so and offers unarchiving or retitling it in Hermes, or `--session <id>`, with no upgrade suggestion. If the row cannot be read, or is not archived, the error gives both possibilities, an archived holder on a gateway older than v2026.9.21 or some other writer, and names `--session` as the way around. Hermetic never unarchives a session itself, since whoever archived it did so on purpose (`packages/core/src/render/hermes-canonical.ts`, `unlistedHolder`; `packages/core/test/bot-mode.test.ts`).

A hosted-room Stop sends a fresh `cancel_id` each time. Upstream defaults an absent `cancel_id` to `"desktop-stop"` (`tui_gateway/methods_groups.py:429-434`) and derives the stop fence's event id from it (`gateway/hosted_rooms.py:1028-1037`), so every Stop after the first in a room would replay the first fence instead of superseding later work. Hermetic sends `hermetic-stop-<uuid>` (`packages/core/src/chat/bot-mode.ts`, `rooms.control`; test in `packages/core/test/bot-mode.test.ts`).

Upstream validates room ids, event ids and `cancel_id` with `IDENTIFIER_RE`, `^[A-Za-z0-9][A-Za-z0-9._:-]*$` (`gateway/hosted_rooms_common.py:19`, applied at `gateway/hosted_rooms.py:206-208,1032`), each capped at 128 characters (`gateway/hosted_rooms.py:24-25`), so an id must start with a letter or digit. Upstream strips surrounding whitespace before matching; Hermetic refuses it instead, so the id sent is the id stored. Upstream also refuses the member handles `all` and `everyone`, because `@all` and `@everyone` address the whole room (`gateway/hosted_room_discussion.py:263-270`). Hermetic checks all of this before the request leaves the laptop (`packages/core/src/schema/bot-mode.ts`: `RoomId` and `EventId` apply `IDENTIFIER_RE` at 128, and `RoomCreateInput` refuses a member whose bot name is `all` or `everyone`, in any case, since a member's handle is its bot name). Upstream compares handles case-insensitively, so two members whose handles differ only in case are also refused as duplicates, and so are `default` and a legacy profile directory named `hermes`, which share `@hermes`. Tests: `packages/core/test/bot-mode.test.ts`.

## Validation boundary

Recorded transport tests validate exact payloads and scope. Fixture tests exercise Hermetic's core, RPC and UI behavior without AWS, model calls or real profile mutations. A fixture passing cannot prove that an individual deployed gateway advertises a capability or has RoomLink configured. The interface must preserve that distinction and expose unsupported operations as unavailable with a reason.

The capability probe, the idempotency contract and the tail-read gap above are each qualified against the pinned source only: the file and line cited is where the behavior is defined upstream, not where it was observed running. `bots.capabilities`, room-send idempotency and the tail-window read are exercised against Hermetic's own fixture double, which asserts they call the right method with the right scope and interpret the right response shape — it does not prove that a deployed gateway at this pin actually answers that way. Neither is live-validated: no run in this contract note reached a real Hermes gateway. Treat "source-qualified" and "fixture-validated" as two different, weaker claims than "live-validated."

The teammate-messaging, mention, silence, rename and lifecycle contracts above are held to the same standard, and no stronger. They are source-qualified: each cites the file and line at `v2026.9.24` where upstream defines the behavior. They are fixture-validated: the shared silence matcher replays upstream's own test cases, `packages/core/test/bot-delivery.test.ts` and the UI suites run the delivery, exchange, mention and silence paths against the fixture backend (the `atlas` bots Marshall and NickQABot exchange a `message_agent` delivery, and `kestrel` has a silent turn; `packages/core/src/backend/fixture/fixture-chat-roster.ts`), and the rename, create, archive and Stop requests are asserted against a recording double. The fixture also shows a refused delivery with Retry (Marshall to `remy@laptop`, `runtime_offline`; `packages/core/src/backend/fixture/fixture-chat-dms.ts`), which exercises the marker and the Retry request, not an upstream refusal. None of them is live-validated. In particular, no run observed a real bot call `message_agent`, a real gateway hold back a streamed marker, a real `profiles.configure` conflict between Hermetic and Desktop, or a real archive followed by a new Bot Chat claiming its title. The failure-reason labels are Hermetic's own wording over upstream's codes, the unarchive hint depends on the dashboard's `GET /api/sessions/{id}` answering as sourced, and the "never retried" and "retryable" flags follow upstream's policy as read, not as observed.
