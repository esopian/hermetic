# UI brief — hermetic dashboard

This document is the visual spec: look, layout, and interaction standards for the app's dashboard page. Source of behavioral truth: `docs/design.md`; where they disagree, the spec wins. The built UI plus this brief are the reference. Design decisions that overrode an earlier draft are listed at the bottom.

## Look

Brutalist terminal-ops aesthetic. Dark default, light theme via `data-theme="light"` on `<html>`/`<body>`; persist choice in localStorage.

Tokens (copy verbatim):
```
dark : --bg:#0e0e0d --bg2:#161614 --bg3:#1f1f1c --fg:#f1efe9 --fg2:#a8a59c --fg3:#6b6963 --line:#2c2b27 --line2:#3d3b35 --acc:#ff5a1f --acc-fg:#0e0e0d --ok:#37c27f --warn:#e8b03a --bad:#ef4d3f --sel:#22211e
light: --bg:#f1efe9 --bg2:#e8e6df --bg3:#dedbd2 --fg:#111110 --fg2:#57554f --fg3:#8b8880 --line:#cfccc3 --line2:#b9b6ac --acc:#ff5a1f --acc-fg:#111110 --ok:#188a55 --warn:#b07a12 --bad:#c9352a --sel:#e3e0d7
```
- Fonts: `Archivo` (display/body, weights 400–900, tight negative letter-spacing on big numerals) + `JetBrains Mono` (all identifiers, IPs, versions, timestamps, CLI strings). Both are vendored in `packages/ui/fonts/` and declared in `fonts.css` with system fallbacks; the page fetches nothing at render time.
- Zero border-radius anywhere. Borders are the structure: `3px solid var(--fg)` for major seams (header bottom, drawer left edge, drawer header/footer), `2px solid var(--fg)` for buttons/inputs/section dividers, `1px solid var(--line)` for rows.
  - **One exception, and only one: the chat avatar.** Three styles ship, seeded from `fleet_id/instance/bot` and never from the display name; the default is `blob`, which is a curve. It is allowed because an avatar is not a control, a surface or a seam — it is a face, and it is the only element on screen for which roundness carries meaning rather than decoration. `DEFAULT_AVATAR_STYLE` in `packages/ui/src/chat/components/avatar/avatar-seed.ts` is the whole switch; `sigil` is the square-built alternative if the curve is regretted. This exception is written down in both places deliberately: a rule with one stated exception is still a rule, and a rule with one undocumented exception is a bug somebody later "fixes".
- Kicker labels: `10px / 700 / letter-spacing .14em / uppercase / color var(--fg3)`.
- Primary button: `background var(--fg); color var(--bg); 900 weight; uppercase`; hover → `background var(--acc); color var(--acc-fg)`. Secondary: `2px solid var(--fg)` outline. Destructive: outline `var(--bad)`, hover fills `var(--bad)`.
- Status dot = square (`8–14px`, no radius). Busy states pulse: `@keyframes hpulse{0%,100%{opacity:1}50%{opacity:.25}}` 1.2s. Drawers slide in from the right (`hslide .18s`), popovers fade (`hfade .12s`).
- Scrollbars: 10px, thumb `var(--line2)`.

## Layout (top to bottom)

1. **Header** (64px, grid `auto 1fr auto`, bottom border 3px):
   - Left: 14px orange square + `HERMETIC` (22px/900/uppercase). Right border 2px.
   - Middle: the **view nav**, `FLEET | CHAT | SETTINGS` (`ViewNav.tsx`, passed to `Header.tsx` as `nav`), full header height, selected = `fg` bg, 1px `--line` separators. The Fleet badge is the agent count (mono), plus `· <n> loose vols` in `--acc` while any volume has no agent — the alert the old Volumes tab carried, kept where it cannot be missed. On the selected (inverted) tab the suffix takes the tab's foreground instead of accent ink. It is drawn on Settings too, so leaving Settings is the same click as arriving; it is absent before `init`, on the fleet picker and in the wizard, where there are no views. The keyboard shortcuts that switch views are unchanged. Below 860px the nav drops to a second header row. There is no separate view-nav row any more.
   - Right: the notification bell and the theme toggle (mono, `☾ dark` / `☼ light`) — nothing else. `+ NEW AGENT` is a fleet action and lives in the fleet toolbar (3), so it does not show on Chat and Settings where it meant nothing.
2. **Env strip** (28px, full width, background = env color, text `#0e0e0d` mono 11px/700/uppercase/.06em, never dimmed): critical facts only — `● FIXTURE` (fixture mode only), the **fleet button** (`FLEET <alias ?? fleet_id> ▾`), `<account>`, `<region>`, the foundation pill when one applies, and right-aligned `tailnet <tailnet> · ● <connected|reconnecting>`. No sentence of prose. Env color: default `var(--acc)` orange (there is no prod/staging concept in the spec; a single frozen target is always "live"); in fixture mode `#8f8c84` grey, plus the `FIXTURE` marker in words.
   - The **fleet button** (`FleetMenu.tsx`) is the fleet switcher's trigger: a 1.5px `#0e0e0d` outline on the env colour so it reads as a control, darkened ground on hover and while open, `aria-haspopup="dialog"`/`aria-expanded`. It opens the **fleet switcher popover** anchored under it: every fleet `fleets.list` (§4.8) knows — name, region, status, a foundation "update available" warn square when that fleet's directory-recorded version is behind — with the current fleet highlighted, a default marker and a "make default" action beside any non-default row, and a per-fleet "Switch" action with an inline confirm. A fleet that is `registered && !local` (known to the account but never attached on this laptop) renders disabled with the hint `hermetic init --attach --fleet <fleet-id>`. Each row is labelled `alias ?? fleet_id` (§4.6) and keyed, compared and acted on by `fleet_id`. Below the list: the frozen config for the *current* fleet — profile, account id, alias, org id, region, fleet_id, frozen_at/by — a `doctor` run and checklist, and `SETTINGS →`. Esc and click-away close it and focus returns to the button. Popover chrome: 3px side/bottom borders, `bg2` 34px section headers, 62px rows. In the wizard the fleet is named but is not a button.
3. **Toolbar** (padding 28px 24px 18px, bottom 1px line): kicker `Fleet · <region>`; the headline is a three-way **lens switch** `<n> AGENTS | <n> VOLUMES | <n> DESTROYED` (the destroyed count only once the lens has read it; numbers 44px/900, labels 18px/800 uppercase; the unselected half `--fg3`, the selected one `--fg` with a 4px `fg` underline; `aria-pressed` buttons). The volumes half carries `<n> free · $<n>/mo` in mono 11px `--acc` when anything is loose, and `scanning…` before the first inventory read. The legend under it is per lens. **Agents**: squares for `n ready` (ok), `n degraded` (warn), `n in progress` (acc; = creating/bootstrapping/stopping/destroying), `n stopped` (fg3), plus `n unreachable` (bad) when > 0, and the loose-volume eye toggle (see Volumes). **Destroyed**: one mono `--fg3` line; the lens is read-only. **Volumes**: `n no agent · <GiB> GiB` (acc), `n ambiguous` (bad), `n detached · agent exists` (warn square), `n attached` (fg2, ok square, always shown), `n not this fleet` (fg3) — each only when > 0 except attached. Right: one filter input shared by both lenses (260×40, 2px fg border, mono 12px; placeholder `filter by name, hostname, version, size…` on agents and `filter by volume id, agent, size, az…` on volumes), the layout switch — `BOARD | TABLE | TRIAGE` on agents (board is the default), `LANES` plus a `REFRESH` button on volumes — (2px fg border, selected = fg bg), then a 1px `--line2` divider and **`+ NEW AGENT`** (`btn-primary`, 40px, with a dim mono `N` key hint) as the last control on both lenses. It opens the same create drawer `n` does.
4. **Fleet body** (flex:1, scroll). On the agents lens, three layouts, all click a row → detail drawer (on the volumes lens, the lanes below under Volumes):
   - **Table** (min-width 1480, sticky header row 10px kickers, 2px bottom border; rows 56px, 1px line): columns `Agent` (2-digit index in mono fg3 + name 16px/800 + `NEW` orange tag for just-created), `Status` (square + uppercase 12px/800 in status color), `Health` (three 14px squares: hermes, tailscale, disk — ok/warn/bad/fg3-when-stopped/line2-when-pending), `Version` (mono; warn color when hermes_version ≠ fleet latest), `Size` (boxed `S`/`M`/`L` glyph 2px fg border + instance type mono fg2), `CPU`, `Mem` (mono % + 4px bar, color: >85 bad, >70 warn, else fg2), `Tailscale` (hostname `<name>.<tailnet>.ts.net` + ip fg3), `Uptime`/heartbeat age, `Disk` (right aligned % + 60px bar). Stopped rows opacity .55. Selected row bg `var(--sel)`.
   - **Board**: `repeat(auto-fill, minmax(300px,1fr))` cards, 2px `var(--line)` gutters, `border-top: 4px solid <status color>`, name 22px/900, hostname mono, status line, footer with health squares (18×8) and version.
   - **Triage** (grouped): sections `attention` (warn: degraded, unreachable, or behind latest), `in progress` (acc), `healthy` (ok: ready + latest), `stopped` (fg3); left 220px column with label, 48px count, hint text; right side 48px rows.
   - **Empty**: centered `NO AGENTS HERE` 26px/900 + mono hint. A fleet with no agents at all adds a large `CREATE YOUR FIRST AGENT →` primary button (48px), because the toolbar's button is easy to miss on a blank page; with no ready provider profile it is `SET UP A PROVIDER →` instead.
5. **Footer** (10px 24px, mono 11px fg3): status only. Two squares, each a colour and a word — `■ fleet` (the `fleet.subscribe` stream) and `■ volumes` (the inventory read) — coloured `--ok` (reading on cadence), `--warn` (stale: no read for three of its own intervals, or the stream dropped and is retrying), `--bad` (the last read failed) or `--fg3` (nothing read yet); a square pulses while a read is in flight or the stream is reconnecting. No ages on the line: the last read time, the error and the retry countdown are the square's tooltip. Then the app-update notice when there is one, and right-aligned `? for shortcuts`, which opens the same keyboard sheet `?` does.

## Volumes (§9.1)

A volume outlives the agent that made it, so the dashboard has two jobs: the **agents lens notices**, and the **volumes lens works**. Both are the fleet page — Volumes is not a view of its own.

- **Volumes lens.** The fleet toolbar's `<n> VOLUMES` half (Layout 3). `location.hash === "#fleet/volumes"` addresses it; the old `#volumes` still lands on it and is rewritten in place (`replaceState`, no history entry). It is a lens, not an overlay: Esc never closes it, and Settings or Chat opened from it come back to it. Opening an agent (a notification, "Go to <agent> →") puts the fleet back on its agents lens, since the drawer belongs to that one; back from `#agent/<name>` to `#fleet/volumes` closes the drawer.
- **Fleet board.** Every agent card's footer swaps its health squares for a **Data volume** line — `vol-0a91… · 100 GiB · attached` in `--ok`, or `· detached` in `--warn` with the kicker reading `Data volume · safe`. Before the first volume read the line shows the id alone in `--fg3` and claims no state.
- **Tombstones.** A volume in the `no_agent` group is a dead agent that kept its memory, drawn where that agent used to be: a `card` with `border-top: 4px dashed var(--fg3)` and a 135° 10px hatch, the agent tag as the (dimmed) name, the volume id as the hostname line, `MEMORY KEPT` in `--acc`, snapshots in the footer and one button — `CREATE AGENT →`. **No delete button**: beside "Create agent" it is one mis-click from destroying the thing you came to reclaim. Three rules decide what appears: only `no_agent` (an ambiguous volume might be an agent's memory, but a tombstone says *which*); never one a live agent on screen owns (its own card carries it; a destroyed agent has no row, §6.7); capped at 4, newest-free first, then one `+ N more volumes` card whose `ALL VOLUMES →` switches to the volumes lens. Tombstones stay on the agents lens; the volumes lens is where they are seen in full.
- **Toolbar.** On the agents lens, a legend entry `<n> volumes with no agent · ≈ $<n>/mo` in `--acc` with an eye toggle, shown only when the count is > 0. The agents half of the headline counts agents only: volumes are not agents.
- **Fleet table.** The `Disk` column becomes `Data volume` (the percentage lives on in the drawer's metric tiles). Volumes with no agent land in a bordered `VOLUMES · NO AGENT` block below the last agent row — `border-top: 2px solid var(--fg)`, `bg2`, the count/GiB/cost line and an `ALL VOLUMES →` button — then one 54px row each, ending with `CREATE AGENT →`.
- **Volume lanes.** The volumes lens's body, under the fleet toolbar (headline, legend, filter and refresh are the toolbar's): lanes of a 210px label column (kicker, 46px count, hint) beside the group's rendering. Order is core's: `no agent`, `ambiguous`, `detached · agent exists`, `attached`, `not this fleet`, then a `snapshots` lane. The first three render as `claim` cards (`border-top: 4px` in the lane colour, mono id, agent + tag, a `kv` of free-for/size/snapshots/cost, and a footer of actions); `attached` and `not this fleet` collapse into 48px rows, because they restate what the fleet already shows. Ambiguous cards carry no action — each names its twin and the `hermetic:role=data` tag that settles it. Empty state: a green square, `NOTHING LOOSE`, and the line about destroyed agents keeping their volumes.
- **Create drawer, entered from a volume.** The same drawer, not a second one. The volume segmented picker becomes a locked row (2px `--line2`, `bg2`, mono id, size/AZ/snapshot sub-line, `no CreateVolume` ghost tag); the name is prefilled from the volume's owner tag (`agent`, or `hermetic:former_agent` on a volume a destroy kept), or the next free variant of it when a live agent already holds that name — a destroyed agent's name is free again (§6.1, §6.7), so `cinder`'s memory comes back as `cinder` unless someone has taken it, and the hint says so when it falls back to `cinder-2` rather than only reporting "already exists". A `--warn` note states that the volume's tag moves to the new name as part of the create, is recorded as an event, and is not confirmed twice. The CLI echo becomes `hermetic agent create <name> --volume <id>`.
- **Delete drawer** (620px). One stage: a `--bad` callout naming whose memory it is, a `kv` of volume/size/state/snapshots(**kept**)/saving, a `.name-input` for the volume id with a live `matches` line, and a `--bad` button disabled until it matches. Reachable from the claim card and nowhere else; Esc closes it back onto the volumes lens.
- **Polling.** `volumes.list` is read on its own 60s interval (`VOLUME_POLL_MS`), not the fleet tick (also 60s, `POLL_INTERVAL_MS` in `packages/app/src/poller.ts`): it is two `DescribeVolumes` plus a `DescribeSnapshots` against EC2, while the fleet stream is a scan the main process already does. A create-onto-a-volume and a delete both refresh it immediately. A failed read leaves the last good inventory on screen with a one-line notice and never takes the fleet down with it.

## Chat (§9.2)

`docs/design.md` §9.2 governs chat behavior; this section describes the entry surfaces. The full view, dock and agent drawer's Chat section share the same thread renderer and state. Chat keeps the settled `data-skin="soft"` treatment and blob avatars inside its body. The fleet header, environment strip, navigation and overlay chrome keep the surrounding visual language.

- **Full view.** `CHAT` sits between Fleet and Settings. The rail addresses bots within instance buckets; a conversation carries its session origin into the thread and composer.
- **Dock.** A compact frame keeps the current page visible and survives navigation between Fleet (either lens) and Settings. Expanding to the full view or opening the same conversation in the drawer preserves the draft and turn. Closing the frame hides it; stopping a turn is a separate action. Attempts to change conversations during a live turn explain that the current turn must finish or be stopped first.
- **Agent drawer and fleet links.** The drawer's Chat section renders the same conversation without a second history or composer state. Fleet chat links and `t` use the agent in context and default to its `default` bot.
- **Quick jump.** The `.qj-` chrome is shell chrome. Command-K or Control-K opens the field from anywhere, including another input; Command-Shift-K or Control-Shift-K toggles the dock. `@` narrows to agents and bots, `#` to channel-origin sessions, and `>` offers existing navigation commands. Message search is labelled as searching loaded messages, never all fleet history. Text entered after a target can send directly only for an established in-app destination; otherwise it opens as a draft in the composer, which states the destination before the operator sends.
- **Destination at the composer.** The composer restates where a reply goes only where sending has a consequence or is blocked. `routine`, `peer` and `channel` put it on the send button in warn ("Send · new session", "Reply to <bot>", "Send to <channel>"), with a footer fragment after "over the tailnet · <name>" for what the button has no room for (the routine will not see it; it leaves the tailnet). `desktop` and `room` get only a muted footer fragment. `portal`, `hermetic` and `cli` say nothing; the thread header's origin badge is their only trace. A session read in flight, a bot with no conversation of this portal's, and a failed read each get a slim one-line band (headline and badge, the `unchosen` one with a chip per session to reply into) and disable sending until the destination is known. Moving a thread into a smaller frame cannot remove any of this or assume a local origin.
- **Links and keys.** Links use `#chat/<instance>/<bot>` with optional `session` and `message` query parameters; `#chat/<instance>` defaults the bot. `c` opens the conversation picker and `j`/`k` move through the chat roster. The earlier notification decision still applies: `n` creates an agent, `i` opens the notification centre, and `⇧I` opens the full inbox drawer. Inside the centre and the drawer, `j`/`k`/`↑`/`↓` move focus, `↵` opens, `e`/`⌫` clears, `r` toggles read, `s` snoozes, `m` mutes, `z` undoes, `⇧R` reads everything in view and `⇧E` clears everything read in view; `1`–`3` switch the centre's tabs and `i` closes it; `x` selects and `⇧A` selects all in the drawer. Those keys are captured while the surface is the topmost overlay and never reach the page's own shortcuts under it. Unmodified bindings stay inactive inside fields. Scratch sessions, broadcast and approval responses ship as `chat.respond` / `rooms.respond` (§9); this surface advertises only the commands that exist.
- **Background-process events.** Hermes' injected notices (a command finished, a watch matched, subagents returned) are rows in the thread, not bubbles, and never read "You". A dashed gutter line runs down the left; the row is one mono line — status square (green ok, red failed, muted terminated or info), the command shortened, status and exit code, a duration only when known. Output is collapsed on every row, failures included, with `output · N lines · last line: …` as the summary (a failure's last line in red); a watch match opens with its matched lines. A DM reply is a card headed `<profile> → <this bot>` with the reply as its body, and is never folded. Consecutive routine events fold into one burst row that expands in place. An event and the call that started it link by process id (`started ↑` / `result ↓`); a bot turn right after an event opens with `↳ responding to …`. A per-thread density switch in the thread header (compact, failures only), shown only in a thread with events, hides routine events only. The rail preview reads as one sentence (`↩ lead-qa: …`, `■ bun test exited 1`).

## Drawers (fixed right, backdrop `rgba(0,0,0,.55)`, Esc closes)

**Create** (560px) — quick create + customize. Header: kicker `New agent` / title `CREATE AGENT` 26px/900, `×` 40px boxed. Env strip repeated with `Target · alias · account · region`. One short screen for the common case (name, brain, preset, Create), everything else behind one disclosure. `CreateDrawer.tsx` composes `components/create/*`; state is `create/useCreateForm.ts`, what is sent is `logic/create-form.ts`, presets are `logic/create-presets.ts`; styles in `styles/create.css`. Form (gap 20px):
- **Agent name**: 56px input, 3px fg border, mono 22px/700, auto-focus, dice button inside its right edge; one hint line below (mono 11px): default `lowercase, digits, dashes · becomes the EC2 tag, SSM path and tailnet hostname`; taken → `“x” already exists` in bad; invalid → rule text in bad; valid → `✓ <name>.<tailnet>.ts.net`. Lowercase on input. Validation regex is the spec's: `^[a-z0-9][a-z0-9-]{0,30}$`, not `_fleet`.
- **Brain** (`profile · model`): one 48px 2px-fg row button — ok square + profile name, mono model, then a dashed `fleet default` tag (fleet's default profile, profile's own model) or an orange `model override` tag, then `▾`. It opens a popover (`Popover.tsx`, label `Brain`): left column the *ready* profiles (name + provider label, `· fleet default` on the default; selected = `--sel` bg + 4px acc inset) and a `Manage providers →` row that saves the draft and detours to Settings → Providers; right column the shared `ModelPicker` over the chosen profile's catalog, plus `Back to <profile>’s own model` when overridden; `Done` closes. One hint line under the row: the creds fact (`<ENV> copied from <profile> into this agent's own slot, tmpfs only` / `IAM instance role · no stored secrets`), the override note, or — warn — `…needs a profile chosen` when nothing ready is selected. No ready profile at all: the row is replaced by the `Set up a provider →` callout (draft saved), and Create stays disabled.
- **From a volume**: a `Data volume · locked` row above the presets (mono id, size/AZ/snapshot sub-line, `no CreateVolume` ghost tag, one-line mount note, the `--warn` tag-move note when renaming).
- **Preset** (`size + data volume + system disk`, with an `Edit presets →` link at the right of the label that saves the draft and opens Settings › Create presets): a strip in a 2px fg frame of this laptop's **loadout** (§4.6) — its filled slots, left to right, empty slots skipped; the built-in loadout is `LIGHT` (small, 50 GiB, 20 GiB root), `STANDARD` (medium, 100 GiB, 40 GiB root), `HEAVY` (large, 200 GiB, 40 GiB root), `GPU` (gpu-xsmall, 100 GiB, 40 GiB root). Each cell: uppercase 14px/900 name, mono `size · data GiB`, mono `vCPU · mem`, and the whole machine's price 22px/900 `$N/mo` (instance + data volume + system disk, gp3). Selected = fg bg. The drawer opens on the loadout's **default** preset. Every preset — Standard included — sets and states exactly its three fields, so an untouched create sends them explicitly. A custom preset whose size this build does not know is drawn disabled (`unknown size`). On a locked volume a preset never changes the volume and is priced with the volume's own size. When Customize edits diverge from the selected preset, it shows an orange `+ N changes` chip (fields that differ from it or were reset to inherit). A loadout with every slot emptied replaces the strip with one mono line, and the machine follows the fleet's defaults.
- **Customize** disclosure (2px line2 border, fg when open): collapsed shows `▸ CUSTOMIZE`, a summary (`everything at fleet default` / `N fields changed`) and a mono line `machine · storage · behaviour (secrets, on failure, approvals)`; opens on its own when a restored draft had already changed something. Open, it has `Reset all` (machine back to the preset, everything else to the fleet; `Reset all to fleet default` when there is no preset) and three groups (kicker heading, 1px top rule): **Machine** — size cells (3 primary, `MORE SIZES (N CPU, N GPU) →` expands the other CPU and the GPU cells, pre-expanded when the value is not primary); **Storage** — data volume segmented `50 | 100 | 200 | 500 GiB` (fleet default unioned in, price stacked under each; hidden on a locked volume), system disk slider (8–500 GiB, readout `N GiB · $x/mo`); **Behaviour** — Secrets, On failure, Approvals selects. Size, data volume and system disk carry a `from preset` tag until moved off the selected preset, then an orange `changed · reset` tag whose reset puts the preset's value back (still stated). Secrets, On failure and Approvals carry a dashed `fleet default` tag until touched, then `changed · reset` (reset untouches: the value re-seeds from the fleet and the field leaves the request); the label turns acc when changed. The collapsed summary reads `from <Preset>` while nothing has moved. At most one hint line per field (e.g. `~6 GiB used by Ubuntu + Hermes + browser, leaving ≈N GiB · replaced on every rebuild`). An unread fleet default renders as `fleet default`, never this build's constant, and is priced nowhere.
- Facts line (mono 11px, ok square): `Tailscale only · 0 inbound rules · no SSH key · Hermes <ver> · Chromium · noVNC desktop`.
- Sticky footer (3px top border): the CLI echo on its own mono line (`$ hermetic agent create <name> …`, flags exactly the stated fields); then `TOTAL` kicker + `≈$N/mo` 26px/900 (whole machine; `fleet default` when any part is unread) with a mono sub-line `~$x/h · ready in ~8 min` or `~$x/h · N changes from <Preset>`; then `Cancel` and `CREATE AGENT →` primary (52px, disabled opacity .35).

**Create → Progress** view (same drawer): name mono 28px, sub `t4g.2xlarge · 100 GB data volume · us-west-2`, big `NN%` (44px/900, acc → ok when done), 10px progress bar, step list (14px squares: ok done / acc pulsing current / line2 pending; timing in mono fg3) driven by OpEvent `phase`s from the op stream, then a log pane (`#0a0a09` bg, `#d8d5cc` text, 2px line2 border, mono 11.5px, blinking orange caret) of event messages, footer text `Safe to close — the operation continues in the engine and the row keeps updating.` and button `RUN IN BACKGROUND` (outline) → `BACK TO FLEET` (filled) when done. The op continues in the main process; reopening an agent with a running op re-attaches to it with `ops.subscribe`.

**Agent detail** (840px) — a small settings app (`AgentDrawer.tsx`, sections under `components/agent/`). **Header** (compact, `16px 24px`): status pill (square + status, 11px/800 uppercase) and `hostname · ip` mono on one line, the name 26px/900 uppercase under it, the stale-device / legacy-name note in `--warn` mono when there is one; right-aligned `Dashboard ↗` and `Open desktop ↗` (`btn-sm` secondaries; the desktop one a real `<a href>` to `/vnc/` that the app hands to the system browser) and the close box. Env strip below with alias/account/region and `size · instance type` right-aligned. **Left nav** (190px, `border-right: 3px solid var(--fg)`), a vertical tablist in this order: `Overview · Chat · Desktop · Logs · Config · Lifecycle`, each entry 13px/800 uppercase with a 10px mono sub-line that reads the section without opening it (`all checks ok` / `bootstrap failed`; `listening` / `not listening`; `not connected`; `activity · journal · console`; `<profile> · <model>`; `● upgrade available` / `● rerun available` in `--acc`). The selected entry is filled `--fg` on `--bg`. The section rides in the hash (`#agent/<name>/<section>`, `nav/agent-nav.ts`; Overview is the bare `#agent/<name>`, and the old `overview`/`desktop` spellings still land). Under the list sit the Listen switch and, when the instance is not watched, "Listen to enable this instance's bots in chat and alerts."; the Chat entry is disabled until it is. The nav foot is the CLI echo (`$ hermetic agent status <name>`, `$ hermetic logs <name>` on Logs). **Op rail**: `OpProgress` plus the failure bar are pinned at the top of the right column above every section, so an op started on Lifecycle keeps reporting while the operator reads Logs. Sections (`padding: 20px 24px`, 18px gap), each opening with a kicker and a 15px sentence:
- **Overview** — `Status`: one sentence on what is happening or what is wrong (`agent-summary.ts`: "Ready and serving chats.", "Bootstrap failed at Data volume.", "Not answering.", …), coloured by tone, with `Go to Lifecycle →` when the fix lives there; a `--warn` callout `Hermes <v>. <latest> is available. ## Init wizard (§4.7)

Step 1 (profile): profile list + region override only, no network call. Picking a profile row or editing the region invalidates any prior check for the old combo but does not itself fetch anything. `Continue →` is enabled as soon as a profile is selected.

Step 2 (verify the account): entering the step immediately fires `init.identity` for the chosen profile/region (a cached result for the same combo is reused if you go Back to step 1 and return unchanged; picking a different profile or editing the region invalidates it, so the check reruns on the next visit). Stale in-flight responses are dropped by a monotonic request counter, so a fast Retry or profile change can never let an old answer land after a newer one. One 3px-fg-bordered panel with a fixed min-height (so the layout doesn't jump) renders one of three states:
- **processing** — 14px orange square pulsing, title `CONNECTING`, mono sub-line `sts get-caller-identity · profile <name> · <region>`, a thin 4px indeterminate bar (a 30%-wide orange segment sweeping left→right, `hsweep` 1.2s), a greyed skeleton of the identity card so nothing reflows when it resolves, and a fg3 hint `An SSO profile may open a browser login.`
- **confirmed** — square turns `var(--ok)` (stops pulsing), title `CONNECTED`, the identity card fades in (`hfade`): account id (34px mono), alias, caller ARN, org id, profile · credential type, region; then the foundation line (`Foundation \`hermetic\` found · fleet <id> · <region> → will ATTACH` or `No foundation in <region> → will CREATE one (CloudFormation stack \`hermetic\`)`) in a left-bordered callout (3px, ok color for attach, acc color for create). Below that, the verify toggle row fades in (styled like the segmented controls — 3px fg border, 56px tall, square 22px checkbox that fills `--ok` when ticked, 800-weight label): `I verified this is the account I intend to operate: <account_id>`, with a mono sub-line `hermetic freezes this home to this account. Every create, upgrade and teardown will run here.` Continue is disabled until checked; unchecking, going Back, or changing the step-1 profile clears it.
- **error** — square `var(--bad)`, title `COULD NOT CONNECT`, a mono `<code> · <message>` in a `#0a0a09` log-style box, and two buttons: `RETRY` (primary, reruns the check) and `BACK` (outline, returns to step 1). No toggle is shown and Continue stays disabled.

The wire body still sends `account_id_typed` (now `identity.account_id`, since core re-verifies against STS regardless of what the UI collected).

The rail is grouped under small kicker headers in a fixed order — **FLEET** (`Defaults · Providers · Secrets · Tailnet policy`, the header also naming the `fleet_id`), **INFRASTRUCTURE** (`Foundation · Diagnostics`), **THIS LAPTOP** (`Create presets · Chat · Notifications · Runs`), **ACCOUNT** (`Account & fleets`) — with `Danger zone` alone at the foot under a 1px rule, in `--bad`. Create presets counts the loadout's filled slots (from the page's held copy, once it has been read) with no square. Diagnostics, Tailnet policy, Runs, Chat and Notifications have no square.

**The page template (S-1).** Every section is built only from the parts in `Section.tsx`:

- **A · setting rows** (`SettingRow`) — `300px / 1fr / 120px`: bold label and one ellipsised description line left, control right (≤420px), state column far right: `fleet default` / `unstated` / `saves at once` (mono 10px `--fg3`), `changed` + `was …` (`--acc`, and the row gets a 3px `--acc` left edge), or `✓ saved` (`--ok`, 2s, in an always-present live region).

One section at a time is not tidiness: each section's data is its own network read — `doctor` walks EC2 and the tailnet, the policy card reaches api.tailscale.com through the main process, the run log hits SQLite — and a scroll made every one of them happen because somebody wanted to see the account id. Mounting is the load trigger; no section carries a "should I load" flag.

The section rides in the hash next to the view (`settings-nav.ts`): `#settings` is the landing section (`account`) and `#settings/<section>` is any other, so a section is linkable and survives a reload. An unknown section opens Settings on the landing section rather than bouncing to the fleet — a stale bookmark is still a request for Settings. `ViewNav`'s `View` type gains no member: Settings is still one view, and the section is a second axis.

**Saving follows scope.** Fleet-wide form fields (`_fleet.settings`, §4.2) never save on blur: they stage, and go out together from the sticky save bar (`SaveBar.tsx`, 64px, 3px `--fg` seam on top), which appears only when something is staged and reads `■ N unsaved changes · <field names>` opposite `<fleet_id> · rev N  Discard  Save`. A stale form fails rather than overwrites — it submits the `expected_version` it read, and a `409 CONFLICT` turns the bar `--warn` ("Changed on another laptop") with a `Reload` button; `Discard` after a conflict reloads too, since discarding back onto the stale values would otherwise leave no way to reach the real ones. After a Reload the draft survives if the fleet's defaults did not move, and starts again from theirs if they did (there is no "save mine over theirs"). One settings document is held by `SettingsShell` and updated by every save, so a save in one section is immediately the `expected_version` the next section's save uses. The Defaults draft is held by the shell too, so leaving for another section and coming back keeps the staged edits, and the rail marks Defaults with an `--acc` square until they are saved or discarded; a fleet switch remounts the shell and drops it. Laptop-only controls save as they are touched and flash `✓ saved`; no bar ever appears on those pages. List actions (rotate, enable, set default, delete, unmute, make default) are commands: they confirm in place or in a drawer, never through the bar. Reduced-motion preferences disable its transitions.

The list adds a dedicated listening column and a subtle blue highlight for watched rows. The manager uses the standard drawer with checkboxes and Select all / Clear all; Cancel discards its draft, Apply saves only changed instances, and failed saves leave the drawer open for retry. With no watched instances, the fleet shows the existing listening guidance alert.

### Teardown drawer

Opens from the DANGER button, 640px, right-hand, 3px seams (same `Drawer`/`DrawerHead`/`drawer-foot` chrome as every other drawer). Three stages:

1. **Review** — fetches `plan.teardown` with the current option state and re-fetches on every option change. Renders the plan's `summary` (account, region, fleet, stack id, mono) — falling back to `meta.config` for any field an older plan omits — the numbered `steps` (a red square on `destructive` ones), and the non-agents warnings under a `WHAT STAYS BEHIND — DO BY HAND` kicker. If any agent still exists (checked against the live fleet, not just the plan's prose), a red callout lists them and the stage disables everything except `← BACK` (closes the drawer) and `GO TO FLEET` (closes the drawer and Settings). Options are 3px-bordered checkbox rows styled exactly like the wizard's verify toggle (`.verify-row`, ticked box fills `--ok` like every other checkbox in the app): purge SSM parameters (default on), delete DLM snapshots (off), delete leftover data volumes (off, with a red "agent memory and skills are lost" sub-line), reset the local config (on, "returns this home to the init wizard"). A row's sub-line sits *outside* the bordered box (`.td-option-note`), indented to the label column, so a wrapped note never crosses the border below it. The footer carries `<n> steps · <m> destructive` opposite `CONTINUE →`.
2. **Confirm** — a bordered target panel restates what is about to go (account, region, fleet, `<n> steps · <m> destructive`) with the plan's read time and a `Refresh` link, then two required inputs, both `.name-input` (56px, mono): the 12-digit account id and the literal word `teardown`, each with its own live "matches"/hint line. `TEAR DOWN THE FOUNDATION` is `var(--bad)`-filled and disabled until both match — no hold-to-confirm; the two typed fields are the confirmation.
3. **Progress** — `teardown` with the four flags plus `yes: true`, then `OpProgress` on the op stream. The rail is built from the submitted flags (`teardownPhases()` in `useOp.ts`): `agents_check → bucket → stack → [ssm] → [snapshots] → [volumes] → [local] → done`, the bracketed ones present only when their flag was on — a seeded phase is never folded back out, so listing all four would leave grey steps behind on a finished run. On `done ok`: `FOUNDATION REMOVED`, a manual checklist built from the plan's non-agents warnings (Tailscale OAuth client, ACL entries, anything else a flag left kept), and `COPY CHECKLIST` with the same clipboard-then-select-manually fallback the wizard's ACL snippet uses. When `reset_local` was on the drawer polls `meta.get`; when `initialized` flips false the app shell swaps this whole view for the init wizard on its own (the existing `!initialized` check), which is what "closes the drawer" amounts to. With `reset_local` off there is nothing to wait for, so the poll is skipped and the footer offers `CLOSE` instead. On error: the op's `code`/`message` and a `BACK` button to stage 2.

The wizard renders a dismissible grey notice above step 1 when `meta.last_teardown` is present: "Foundation `<fleet_id>` in `<account>/<region>` was torn down at `<time>`. Manual steps remaining: …". Dismissal is stored in `sessionStorage` keyed off `last_teardown.at`, so it reappears if a *different* teardown lands later but stays dismissed across a reload of the same one.

## Data → UI mapping

- statuses: spec values `creating bootstrapping ready degraded stopping stopped destroying destroyed error` + derived `unreachable` (`destroyed` exists only on legacy rows, which no layout shows — §6.7 and the deviations table). Colors: ready ok; degraded warn; unreachable/error bad; stopped/destroyed fg3; everything else acc (pulsing).
- health squares from `health{hermes,tailscale,disk}`; before first heartbeat → line2 pending.
- metrics from `metrics{cpu_pct,mem_pct,disk_pct,root_disk_pct?}` (may be null → `—`). `disk_pct` is `/data`, `root_disk_pct` the box's own root volume — optional, since an older `hermeticd` reports no such key, and absent renders `—`, never `0%`. The fleet table's disk cell prints both as `data / root`, coloured and barred by the fuller of the two (`worstDisk`); the agent drawer's Overview gives each its own tile — Data disk and System disk.
- "latest" hermes version from `meta.get`'s `hermes_version`.
- Live updates: the `fleet.subscribe` stream (`snapshot`, `agent`, `removed`, `poll`), one scan a minute; the footer's fleet square is judged from `poll`'s age. Op progress (`ops.subscribe`) is its own live stream and does not wait on the fleet tick.

## Bot Mode workspace

The full Chat view separates canonical Bots from additional Sessions in the existing application shell. Above the list the rail is three short rows (30px each): the `Bots · N | Sessions` tabs, search with `+`, and the `All | Unread | Needs you` filters; there is no instance-scope switcher and no active-only toggle, because folding instances does that job. It keeps active-turn indicators and adds hosted rooms and creation controls. Instance headers are headings, not rows: flush left on a `--bg2` band, a `▾`/`▸` twisty and the instance name in 11px/800 uppercase, no avatar, the bot count on the right. Bot rows indent 26px so their avatars start under the instance name. Hovering a bot row swaps its timestamp for a pin star (`☆` pin, `★` unpin). Pinned bots sit in an accent-tinted block above the instances, headed `★ PINNED` in `--acc` and closed by a 2px rule, each preview prefixed with its instance in mono. A collapsed header carries the same `ch-unread` badge a row does (`!` when a bot needs you, else the unread total). The right pane shows the selected bot’s scheduled jobs or the selected room’s members. Profile and routine dialogs use the application’s fonts, tokens and controls; keyboard focus stays within an open dialog and returns when it closes. Narrow layouts expose the roster and context as dismissible panels.

Canonical history stays profile-scoped and follows compression; additional chats keep their own drafts and streams. Room drafts survive switching between conversations within the workspace. Profile dialogs edit configuration and expose explicit removal confirmation. Job controls show actual returned state and errors. Rooms use the gateway driver and ordered history, with exact pending-action coordinates. Unsupported cross-instance rooms and membership edits are explained rather than simulated. The compatibility scope lives in `docs/bot-mode-compatibility.md`.
